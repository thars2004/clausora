====================================================================== 1.
PRODUCT IDENTITY
======================================================================

Brand: CLAUSORA Product name: Clausora Category: AI-powered work
intelligence and milestone payment platform

Suggested tagline: “Understand the work. Verify the outcome. Release the
payment.”

One-line description: Clausora turns any project brief, task, workflow,
document, screenshot or approved work artifact into a structured
execution plan with verifiable deliverables, evidence-based reviews,
scope-change detection and human-approved PayPal milestone payments.

Core promise: A client should not have to manually translate a vague
request into a contract, chase updates, decide whether work meets the
agreement, and then separately manage payment. Clausora connects those
steps in one transparent workflow.

IMPORTANT PRODUCT POSITIONING: Clausora is not an escrow provider, bank,
legal-contract authority, autonomous judge or payment processor. It is a
project understanding, agreement, evidence and payment-orchestration
layer. PayPal processes sandbox checkout and payment capture. A real
production launch would require separate legal, regulatory, payment,
privacy and PayPal approval reviews.

2. THE ORIGINAL PRODUCT IDEA
======================================================================

The central innovation is the “Work DNA Engine”.

A user can provide a project in multiple forms: - Plain-language project
description. - Client brief or statement of work (PDF, DOCX, TXT). -
Screenshots of a website, application, dashboard or design. - Public
URLs supplied by the user. - GitHub repository URL or selected code /
commit links. - Task lists, workflow notes, acceptance criteria and
milestones. - Evidence submitted by the service provider.

Clausora analyses the material and creates a structured “Work
Blueprint”: - What is the actual goal? - What are the workstreams? -
What tasks and dependencies are implied? - What deliverables should
exist? - What evidence can demonstrate each deliverable? - What are the
acceptance criteria? - What is ambiguous or missing? - What are the
risks, assumptions and exclusions? - What milestones and payment amounts
have the parties approved?

The system should not simply invent a contract. It should show the AI’s
proposed interpretation, identify missing information and ask clarifying
questions before the client and provider approve it.

The platform then maintains a live relationship between: ORIGINAL BRIEF
-> WORK BLUEPRINT -> APPROVED AGREEMENT -> MILESTONES -> SUBMITTED
EVIDENCE -> REVIEW -> HUMAN APPROVAL -> PAYPAL PAYMENT -> AUDIT TIMELINE

Distinctive feature: “Work DNA / Scope Drift” When new requests,
evidence, messages or task changes appear, Clausora compares them with
the approved Work Blueprint. It classifies each new item as: 1. Already
included in the approved scope. 2. A clarification of an existing
requirement. 3. A likely new deliverable. 4. A deadline or dependency
change. 5. A potentially conflicting instruction. 6. Not enough
information to classify.

If the request appears outside the approved scope, Clausora proposes a
change request with a description, impact, estimated effort (clearly
labelled as an estimate), proposed due-date change and optional new
milestone. It does not silently change the agreement or payment amount.

A second distinctive feature is the “Evidence Graph”: Each acceptance
criterion is linked to evidence items, AI observations, reviewer
decisions and a payment milestone. Users can see exactly why a milestone
is marked ready, needs revision or is awaiting human review.

3. TARGET USERS AND PROBLEM
======================================================================

Primary users: - Freelancers and independent developers. - Small
software agencies. - Startup founders hiring contractors. - Designers,
developers, video editors and digital service providers. - Clients who
need transparent progress and deliverable acceptance.

Problems: - Client requests are often vague or scattered across messages
and files. - Providers and clients may understand the same task
differently. - Deliverables and acceptance criteria are not clearly
defined. - Work evidence is disconnected from the original
requirement. - New requests are added without updating scope or
payment. - Payment approval becomes a manual, confusing final step. -
There is no shared, auditable history of what was agreed and delivered.

Clausora’s value: - Turn unstructured requests into clear work. - Reduce
avoidable misunderstandings. - Make progress measurable. - Connect proof
to acceptance criteria. - Make scope changes visible. - Make payment
conditional on explicit approval and PayPal checkout. - Preserve a
transparent activity timeline.

Do not claim that Clausora eliminates disputes or guarantees work
quality. It improves clarity and traceability.

6. PRODUCT EXPERIENCE / USER JOURNEYS
======================================================================

Roles: - CLIENT: creates project, reviews blueprint, approves agreement,
funds checkout, reviews submitted work. - PROVIDER: accepts agreement,
updates tasks, uploads evidence, requests milestone review. -
ADMIN/DEMO: optional platform-level test role for hackathon
demonstration.

Main journey:

STEP 1 - Create a project Client enters a project name and description,
or uploads a brief/document/screenshots. The app shows supported file
types, upload progress and privacy notice.

STEP 2 - AI Work DNA analysis Backend sends extracted text and supported
image inputs to Hugging Face. AI identifies project type, workstreams,
tasks, deliverables, dependencies, acceptance criteria, risks and
missing information. UI displays a visual Work Blueprint with editable
cards. User can ask follow-up questions and regenerate a section.

STEP 3 - Clarification and agreement Client and provider review the
blueprint. Both sides can request edits. The final approved version is
frozen as an agreement snapshot. Store a SHA-256 hash, version,
timestamp and approving user IDs. A new change must create a new
version; never overwrite the historical approved version.

STEP 4 - Milestone setup User enters milestone names, amounts, currency
and due dates. Server validates total amounts and currency. The project
shows a milestone timeline and payment summary. Only mutually approved
milestones become active.

STEP 5 - Provider performs work Provider updates task statuses and
submits evidence. Evidence can include image, document, public URL,
GitHub commit/PR URL or explanatory note. Store metadata and a
cryptographic hash of the uploaded file where practical. Use private
object storage; do not expose raw storage credentials.

STEP 6 - AI evidence review AI maps each evidence item to one or more
acceptance criteria. It returns supported, partially supported, not
supported or insufficient evidence. It explains limitations. The client
sees an Evidence Graph: criterion -> evidence -> AI observations ->
human decision.

STEP 7 - Human approval Client reviews the evidence and AI
recommendation. Client chooses: - Approve milestone. - Request
revision. - Request more evidence. - Raise a dispute / pause the
milestone.

Only an authenticated client with permission for that agreement may
approve. AI must never call the PayPal payment endpoint or approve a
milestone by itself.

STEP 8 - PayPal sandbox checkout After explicit client approval, backend
creates a PayPal order for the approved milestone. Frontend displays
PayPal checkout / approval action. After payer approval, backend
captures the order. Backend verifies capture response and webhook
events. Only confirmed server-side payment state changes the milestone
to PAID.

STEP 9 - Closeout Show complete audit timeline, agreement version,
evidence, reviewer decision, PayPal order/capture references and paid
status. Allow download of a project completion summary (optional).

7. UNIQUE FEATURES THAT MAKE CLAUSORA STAND OUT
======================================================================

1.  WORK DNA ENGINE Understands the goal and structure of work from
    mixed input types, rather than only generating a contract from a
    prompt.

2.  EVIDENCE GRAPH Links every acceptance criterion to submitted proof,
    AI observations, limitations and human approval.

3.  SCOPE DRIFT RADAR Detects new tasks or changed expectations compared
    with the approved scope. Suggests a formal amendment instead of
    silently changing the project.

4.  DELIVERABLE READINESS MAP Shows which criteria are supported,
    partially supported, missing or waiting for review. Use clear status
    labels, not a misleading single “AI quality score”.

5.  AGREEMENT VERSION FINGERPRINT Creates a SHA-256 hash of the
    canonical approved agreement JSON. Any amendment creates a new
    version and hash. This is tamper-evident recordkeeping, not a
    blockchain or legal signature.

6.  PAYMENT CONDITION ENGINE Deterministic backend rules ensure a
    milestone is eligible for checkout only after the correct human
    approval and permission checks.

7.  AUDIT TRAIL Append-only event records for key actions: agreement
    created, version approved, evidence uploaded, AI review completed,
    revision requested, milestone approved, PayPal order created,
    capture verified.

8.  AI EXPLANATION PANEL For every AI suggestion, show:

-   What was detected.
-   Which source material was used.
-   What evidence supports the suggestion.
-   What is uncertain.
-   What a human must decide.

Backend principles: - Controllers handle HTTP only. - Services contain
business logic. - Repositories/data-access layer handle database
operations. - Middleware handles authentication, role permissions and
validation. - AI adapter isolates Hugging Face provider details. -
PayPal adapter isolates OAuth, Orders API and webhook verification. -

plus ISO currency code. Never use JavaScript floating-point arithmetic
for money. - Store timestamps in UTC. - Use idempotency keys for payment
operations. - Add database indexes for user, project, agreement,
milestone, PayPal order and event IDs.

11. MILESTONE STATE MACHINE
======================================================================

Allowed lifecycle:

CREATED -> IN_PROGRESS -> SUBMITTED -> AI_REVIEWED ->
AWAITING_CLIENT_DECISION

From AWAITING_CLIENT_DECISION: -> REVISION_REQUESTED ->
MORE_EVIDENCE_REQUIRED -> APPROVED_FOR_PAYMENT -> DISPUTED

From REVISION_REQUESTED: -> SUBMITTED

From MORE_EVIDENCE_REQUIRED: -> SUBMITTED

From APPROVED_FOR_PAYMENT: -> PAYPAL_ORDER_CREATED -> PAYER_APPROVED ->
PAYMENT_CAPTURED

Failure paths: -> PAYMENT_FAILED -> DISPUTED

Terminal/closing states: -> PAID -> CANCELLED -> DISPUTED / RESOLVED

Enforce transitions in a backend service. Reject invalid state
transitions with HTTP 409. Never accept a status update from the
frontend without checking the current database state and actor
permissions.

12. AI SERVICE IMPLEMENTATION
======================================================================

Create: api/src/services/huggingface/huggingface.client.ts
api/src/modules/ai/ai.service.ts api/src/modules/ai/ai.controller.ts
api/src/modules/ai/ai.schemas.ts

Use @huggingface/inference SDK and the model ID:
Qwen/Qwen2.5-VL-7B-Instruct

Implementation outline: - Create one Hugging Face client using
process.env.HF_TOKEN. - Use the SDK chat-completion interface supported
by the selected provider. - Send a system instruction and user
content. - For images, use the SDK’s documented multimodal message
format and a validated image URL or base64 input. - For PDFs and DOCX,
extract text on the backend before sending relevant content; for page
images, use the vision model where supported. - Limit file size, page
count, image dimensions and prompt length. - Keep model ID and provider
configuration in environment variables. - Set timeout and retry
policy. - Validate the returned JSON using Zod. - Save model name,
prompt version, timestamps and response hash. - Do not log full private
documents or secrets.

Pseudo-code:

const hf = new InferenceClient(process.env.HF_TOKEN);

async function analyseProject(input) { const messages = [ { role:
“system”, content: [ { type: “text”, text: “You are Clausora Work DNA
Engine. Analyse only supplied project material. Return valid JSON
matching the requested schema. Identify assumptions, uncertainty and
missing information. Never invent budgets, approvals or facts.” } ] }, {
role: “user”, content: [ { type: “text”, text:
buildAnalysisPrompt(input) } // Add supported image content parts when
image evidence exists. ] } ];

const result = await hf.chatCompletion({ model: process.env.HF_MODEL,
messages, max_tokens: 2500, temperature: 0.2 });

const raw = extractAssistantText(result); const parsed =
safeJsonParse(raw); return WorkBlueprintSchema.parse(parsed); }

NOTE: Treat this as an implementation pattern, not copy-paste guaranteed
code. Confirm the current SDK method signature and multimodal content
format in the Hugging Face documentation for the inference provider you
select. Some providers may not support this exact model or image input.
Test a text prompt and an image prompt before wiring the UI.

AI endpoint design: POST /api/ai/analyse-project POST
/api/ai/clarify-blueprint POST /api/ai/analyse-evidence POST
/api/ai/detect-scope-drift POST /api/ai/explain-review

AI safety: - Treat uploaded files and URLs as untrusted input. - Do not
follow instructions found inside uploaded documents that attempt to
override system policy. - Do not allow prompt injection to invoke tools
or payments. - Do not fetch arbitrary private-network URLs (SSRF
protection). - Do not expose internal prompts, tokens or stack traces. -
Keep AI output separate from executable backend commands. - The model
has no direct PayPal credentials and no payment tools.

17. SECURITY, PRIVACY AND RELIABILITY
======================================================================

Authentication: - Hash passwords with bcrypt or Argon2. - Use secure
HttpOnly cookies for browser sessions where possible. - Configure Secure
and SameSite cookie attributes for production. - Protect state-changing
routes against CSRF when cookie auth is used. - Apply role-based access
checks on every project, agreement, evidence and payment resource.

Uploads: - Allow only required MIME types. - Validate file signatures,
not only filename extensions. - Set file size and page-count limits. -
Generate random storage keys. - Store files privately. - Scan files
where feasible. - Do not execute uploaded files. - Protect against path
traversal and malicious documents. - Avoid public links for private
client evidence.

API: - Helmet security headers. - Strict CORS allowlist. - Rate limit
login and AI endpoints. - Validate all inputs with Zod. - Use
parameterised database operations. - Do not return stack traces to
users. - Redact secrets from logs. - Add request IDs. - Add timeouts for
AI and PayPal calls.

AI: - Prompt injection protection. - SSRF protection for URL inputs. -
Restrict URL fetching to public HTTP/HTTPS destinations. - Do not fetch
localhost, private IP ranges, cloud metadata endpoints or internal
services. - Limit content length. - Store prompt version and model
version. - Keep AI outputs advisory.

Payments: - Server-side order creation and capture. - Webhook signature
verification. - Idempotent webhook processing. - Amount/currency
reconciliation. - Permission and state checks. - No card data stored by
Clausora. - Sandbox-only for hackathon.

Privacy: - Explain what data is uploaded and sent to Hugging Face. - Ask
for permission before processing sensitive documents. - Provide
delete/export controls where feasible. - Retain only what is needed for
the demo. - Do not use private user files for model training. - Provide
a demo dataset that contains no real personal or financial data.

ADDENDUM: VERCEL + MONGODB ATLAS DEPLOYMENT
================================================================================

YES — Vercel can work with an online MongoDB database. The recommended setup
for Clausora is:

- Frontend: React + Vite + Tailwind CSS deployed on Vercel.
- Backend: Node.js + Express + TypeScript deployed on Render (or another
  persistent Node.js hosting provider).
- Database: MongoDB Atlas cloud database.
- AI: Hugging Face Inference Provider / configured model endpoint.
- Payments: PayPal Developer Sandbox.

IMPORTANT: Vercel is primarily a serverless deployment platform. It can host
serverless backend functions, but a conventional Express server that expects
to stay running continuously should not simply be deployed as if Vercel were
an always-on Node server. For the current Clausora Express architecture,
deploy the backend separately (for example, on Render) and keep the React
frontend on Vercel. Alternatively, deliberately adapt the backend routes to
Vercel Functions.

OPTION A — CREATE MONGODB ATLAS SEPARATELY (RECOMMENDED FOR CONTROL)

1. Open https://www.mongodb.com/atlas
2. Sign in or create a MongoDB Atlas account.
3. Create a project for Clausora.
4. Create a database deployment/cluster. Select a suitable region close to
   the backend hosting region where possible.
5. Create a database user with a strong password. Do not use your Atlas
   account login password as the application database password.
6. Configure network access. For a hosted backend with changing outbound IPs,
   follow the hosting provider's current networking guidance. Avoid opening
   database access to the entire internet unless it is genuinely required;
   if a broad allowlist is temporarily used, use strong credentials and
   restrictive database permissions, and revisit it before production.
7. In Atlas, choose Connect -> Drivers and copy the Node.js connection string.
8. Replace the placeholder username, password and database name safely.
   URL-encode special characters in the password when required.
9. Add the connection string to the backend hosting provider's environment
   variables as MONGODB_URI.
10. Restart/redeploy the backend and test the database connection.

Example backend environment variable (placeholder only):

MONGODB_URI=mongodb+srv://<db-user>:<db-password>@<cluster-host>/<database-name>?retryWrites=true&w=majority

Do not commit a real connection string to GitHub.

OPTION B — USE THE VERCEL MARKETPLACE MONGODB ATLAS INTEGRATION

1. Open the Vercel project.
2. Open the Vercel Marketplace / Integrations area.
3. Find the MongoDB Atlas integration.
4. Follow the integration flow to connect or provision an Atlas database.
5. Review the selected plan, billing arrangement, permissions and database
   access settings before confirming.
6. Check which environment variables the integration creates and which
   deployment environments receive them.
7. Ensure the variable is available to the server-side runtime that connects
   to MongoDB.
8. Redeploy after environment-variable changes.

The Marketplace integration can simplify provisioning and environment-variable
configuration. Review the current integration terms and pricing: available
cluster types, free-tier eligibility, billing and permissions can change.

ENVIRONMENT VARIABLES — WHERE TO PUT THEM

For the recommended split deployment:

Vercel frontend:
- VITE_API_BASE_URL=https://<your-backend-domain>
- Only public values that are safe to expose in the browser belong in VITE_*
  variables.

Backend hosting provider:
- MONGODB_URI=<your MongoDB Atlas connection string>
- PAYPAL_CLIENT_ID=<sandbox client ID>
- PAYPAL_CLIENT_SECRET=<sandbox secret>
- PAYPAL_BASE_URL=https://api-m.sandbox.paypal.com
- HF_TOKEN=<Hugging Face token>
- JWT_SECRET=<strong random secret>
- FRONTEND_ORIGIN=https://<your-vercel-domain>
- Other server-side configuration required by the application.

SECURITY RULES

- Never put MONGODB_URI, PAYPAL_CLIENT_SECRET, HF_TOKEN or JWT_SECRET in
  frontend VITE_* variables.
- Never expose server secrets in React code, browser bundles, source maps,
  client-side network requests or public GitHub repositories.
- Keep MongoDB credentials in server-side environment variables only.
- Use a database user with only the permissions the application needs.
- Restrict database network access according to the backend host's supported
  networking model.
- Use HTTPS for deployed frontend and backend communication.
- Configure CORS to allow only the actual frontend origin(s).
- Do not trust a frontend response as proof that a PayPal payment was captured.
- Keep PayPal order creation, capture, verification and webhook handling on
  the backend.

MONGODB CONNECTION HANDLING

- Reuse MongoDB connections where possible; do not create a new connection
  for every request without considering connection pooling.
- For serverless functions, use the current MongoDB/Vercel guidance for
  connection reuse and pooling. Vercel functions may scale into multiple
  instances, so set sensible pool limits.
- For a persistent Express backend, initialize and reuse the database
  connection during application startup and handle connection failures.
- Do not assume serverless functions share in-memory state between requests.
- Store durable application state in MongoDB, not process memory.

CLAUSORA DEPLOYMENT RECOMMENDATION

For the first working hackathon deployment:

1. Deploy the React + Vite frontend to Vercel.
2. Deploy the Express + TypeScript API to Render.
3. Create MongoDB Atlas separately and connect it to the backend using
   MONGODB_URI.
4. Configure the frontend's VITE_API_BASE_URL to point to the deployed API.
5. Configure backend CORS to allow the Vercel frontend domain.
6. Add PayPal Sandbox and Hugging Face secrets only to the backend.
7. Test registration/login, project creation, blueprint generation,
   agreement approval, evidence submission, client approval, sandbox payment
   capture and webhook processing on the deployed environment.
8. Confirm the public demo works without relying on localhost or local files.

This split keeps the frontend deployment simple and gives the Node.js API a
more conventional runtime for Express, AI requests, PayPal webhooks and
database operations.
